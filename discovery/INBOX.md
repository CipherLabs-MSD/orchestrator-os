# Discovery Inbox

One human-edited entry point for resource links and ideas across the ecosystem.
Model Lab and the OOS runtime are not dependencies. Domain research registers keep
their authority; this inbox indexes them rather than replacing their decisions.

## Add a link

Ask: **“Lägg i Discovery Inbox: [link] — [optional reason]”.**
An agent updates this file under the repository workflow; this is not an automatic
capture service. Or append a row manually after reading the latest inbox.

1. Search the name, aliases and URL first (ignore trailing slash, tracking parameters
   and GitHub `.git` when comparing). Update an existing row instead of duplicating it.
   Do not merge ambiguous names without evidence. Check domain registers too.
2. Use the next unused ID: **DISC-397**. Never renumber or reuse an ID.
3. Use today's capture date, a short reason, triage `NEW`, execution `UNKNOWN`.
   For an idea use `IDEA` and `Idea — user note`; missing URLs stay `Unknown`.
   Escape literal table separators as `\|`.
4. Record provenance and scope in the notes; do not infer testing from a proposal,
   clone, installed package, or a status called TEST/SANDBOX/ADOPT.
5. Keep only public resources and non-sensitive summaries here. Preserve private
   evidence at its source. Do not install anything or create implementation tasks.

### Article framework (source claims, not verified system capabilities)

- **Level 0 — Chat:** the human supplies the environment, checks results and chooses
  the next step; manual coordination becomes the bottleneck.
- **Level 1 — Harness/tools:** a minimal, documented tool environment enables action;
  additional overlapping tools also introduce choices and failure opportunities.
- **Level 2 — Persistent memory and permission walls:** external progress, attempted
  approaches, checkpoints and artifact references survive context loss. Least
  privilege, isolation, allow-lists and hard budgets enforce boundaries independently
  of prompts; a written instruction alone is not an enforced permission wall.
- **Level 3 — Deterministic verification:** define a check that can fail before work.
  The article ranks deterministic checks above observable traces, independent review
  and self-report; its bug example requires reproduction before and success after.
- **Level 4 — Feedback and bounded retries:** expected versus observed results,
  location, scope fence and dead ends guide correction. Exit on success, repeated
  identical failure (twice in the article's example), or exhausted budget; escalate
  rather than repeat indefinitely. These are proposed heuristics, not adopted policy.
- **Level 5 — Dependency graph and parallel work:** bounded nodes, real dependency
  edges and durable state; parallelize independent work with separate worker contexts.
  Use deterministic code for invariant operations and gates at node boundaries.
- **Level 6 — Evidence gates, frozen successful nodes and risk-based human approval:**
  preserve accepted outputs read-only and retry only failed nodes. Gate strength
  follows reversibility and impact, using checks, traces and independent review;
  irreversible actions require a human in the article. Code enforces authority,
  rather than accepting model confidence as permission. Later adoption would still
  have to obey each system's existing owner policy, including OOS merge authority.
- **Level 7 — Learning into durable rules:** convert lessons into constraints at the
  responsible layer: tool access, memory exclusions, required checks or graph split
  rules. Carry forward concise rules rather than transcripts. The article's claim
  that the same failure never costs twice is an aspiration, not an established guarantee.

### Proposed applications (not adoption or implementation)

- **System-Builder-OS:** use the ladder as a design-review vocabulary; specify what
  counts as green before choosing tools and where reusable durable rules belong.
- **Orchestrator-OS:** compare bounded loops, dependency scheduling, evidence gates,
  immutable accepted artifacts and escalation with existing contracts in a future
  review; documentation or a disposable spike alone does not prove runtime capability.
- **FinanceOS:** distinguish research artifacts from authorized execution, retain
  provenance and reproducible checks, bound research retries and require applicable
  human approval for consequential or irreversible financial actions.
- **Workboard:** explore displaying node dependencies, evidence links, retry budget,
  frozen accepted outputs and approval blockers so displayed completion reflects evidence.
